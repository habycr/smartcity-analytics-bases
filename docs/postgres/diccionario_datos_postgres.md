# SmartCity Analytics — Diccionario de datos PostgreSQL

**Motor:** PostgreSQL 16  
**Alcance:** ocho tablas del modelo lógico relacional.

## 1. Convenciones de implementación

- Los nombres de las tablas y columnas utilizan `snake_case`, sin tildes.
- Todas las tablas pertenecen al esquema `public`.
- Los identificadores compartidos con MongoDB (`id_sensor` e `id_ubicacion`) se almacenarán como `VARCHAR(64)`.
- El contrato de MongoDB confirma que `sensor_id` y `zona_id` son cadenas estables, coordinadas con PostgreSQL.
- La longitud máxima de 64 caracteres es una decisión propuesta para PostgreSQL que debe respetarse o acordarse con el equipo MongoDB.
- Los identificadores internos utilizan `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Las fechas de instalación utilizan `DATE`.
- Las fechas y horas de las mediciones utilizan `TIMESTAMPTZ`, trabajando con instantes UTC.
- Todas las claves foráneas son obligatorias (`NOT NULL`), según las participaciones totales del modelo Chen.
- Se utilizará `ON DELETE RESTRICT` para evitar eliminar registros referenciados.
- Los nombres de categorías, nombres de variables y correos electrónicos serán únicos.
- Los nombres y apellidos de las personas no tendrán restricciones de unicidad.
- `usuario.apellido2` es opcional.
- `sensor.estado` solo admite `activo` e `inactivo`.

## 2. Tablas y atributos

### 2.1. UBICACION

| Columna | Tipo de dato | Permite NULL | Restricciones |
|---|---|---|---|
| `id_ubicacion` | `VARCHAR(64)` | No | PRIMARY KEY |
| `nombre_zona` | `VARCHAR(150)` | No | NOT NULL |
| `distrito` | `VARCHAR(120)` | No | NOT NULL |
| `latitud` | `NUMERIC(9,6)` | No | CHECK (-90 a 90) |
| `longitud` | `NUMERIC(9,6)` | No | CHECK (-180 a 180) |

**Descripción:** almacena la información geográfica de las zonas donde se encuentran instalados los sensores.

**Consideraciones:**

- `id_ubicacion` debe coincidir con `zona_id` en MongoDB.
- El atributo compuesto `coordenadas` del modelo Chen se representa mediante `latitud` y `longitud`.
- Las coordenadas se almacenan en grados decimales.

### 2.2. CATEGORIA_SENSOR

| Columna | Tipo de dato | Permite NULL | Restricciones |
|---|---|---|---|
| `id_categoria` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | No | PRIMARY KEY |
| `nombre_categoria` | `VARCHAR(100)` | No | NOT NULL, UNIQUE |

**Descripción:** almacena las categorías generales utilizadas para clasificar los tipos de sensores.

**Consideraciones:**

- Cada categoría puede agrupar varios tipos de sensores.
- El nombre de la categoría debe ser único.

### 2.3. TIPO_SENSOR

| Columna | Tipo de dato | Permite NULL | Restricciones |
|---|---|---|---|
| `tipo_sensor` | `VARCHAR(80)` | No | PRIMARY KEY |
| `id_categoria` | `BIGINT` | No | FOREIGN KEY, NOT NULL |

**Clave foránea:**

`id_categoria` → `categoria_sensor(id_categoria)`

**Descripción:** define los tipos de sensores y su categoría correspondiente.

**Consideraciones:**

- Cada tipo de sensor pertenece a exactamente una categoría.
- Una categoría puede contener múltiples tipos de sensores.
- El identificador `tipo_sensor` es textual para facilitar la interoperabilidad con MongoDB.

**Dependencia funcional:**

`tipo_sensor → id_categoria`

### 2.4. ORGANISMO_RESPONSABLE

| Columna | Tipo de dato | Permite NULL | Restricciones |
|---|---|---|---|
| `id_organismo` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | No | PRIMARY KEY |
| `nombre` | `VARCHAR(180)` | No | NOT NULL |
| `responsable` | `VARCHAR(180)` | No | NOT NULL |

**Descripción:** almacena los organismos encargados de administrar sensores.

**Consideraciones:**

- Un organismo puede administrar múltiples sensores.
- Cada sensor debe estar asociado a un organismo.
- Todavía debe confirmarse si el nombre del organismo será único.
- El significado exacto del atributo `responsable` se validará con las reglas de negocio.

### 2.5. USUARIO

| Columna | Tipo de dato | Permite NULL | Restricciones |
|---|---|---|---|
| `id_usuario` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | No | PRIMARY KEY |
| `nombre` | `VARCHAR(100)` | No | NOT NULL |
| `apellido1` | `VARCHAR(100)` | No | NOT NULL |
| `apellido2` | `VARCHAR(100)` | Sí | Opcional |
| `correo` | `VARCHAR(254)` | No | NOT NULL, UNIQUE |

**Descripción:** almacena los usuarios registrados en el sistema.

**Consideraciones:**

- `USUARIO` es una entidad independiente.
- Los usuarios no están obligados a pertenecer a organismos responsables.
- El segundo apellido es opcional.
- Los nombres y apellidos pueden repetirse entre diferentes usuarios.
- El correo electrónico debe ser único.
- Está pendiente definir si la comparación de correos distinguirá entre mayúsculas y minúsculas.

**Transformación del modelo Chen:**

El atributo compuesto `nombre` se divide en:

- `nombre`
- `apellido1`
- `apellido2`

### 2.6. SENSOR

| Columna | Tipo de dato | Permite NULL | Restricciones |
|---|---|---|---|
| `id_sensor` | `VARCHAR(64)` | No | PRIMARY KEY |
| `nombre` | `VARCHAR(150)` | No | NOT NULL |
| `tipo_sensor` | `VARCHAR(80)` | No | FOREIGN KEY, NOT NULL |
| `fecha_instalacion` | `DATE` | No | NOT NULL |
| `estado` | `VARCHAR(20)` | No | CHECK, NOT NULL |
| `id_ubicacion` | `VARCHAR(64)` | No | FOREIGN KEY, NOT NULL |
| `id_organismo` | `BIGINT` | No | FOREIGN KEY, NOT NULL |

**Claves foráneas:**

- `tipo_sensor` → `tipo_sensor(tipo_sensor)`
- `id_ubicacion` → `ubicacion(id_ubicacion)`
- `id_organismo` → `organismo_responsable(id_organismo)`

**Descripción:** almacena los sensores instalados en las diferentes ubicaciones de la ciudad.

**Consideraciones:**

- Cada sensor pertenece a un tipo.
- Cada sensor está instalado en una ubicación.
- Cada sensor es administrado por un organismo.
- Un sensor puede existir sin haber generado mediciones.
- `id_sensor` debe coincidir con `sensor_id` en MongoDB.

**Estados permitidos:**

- `activo`
- `inactivo`

**Restricción propuesta:**

```sql
CHECK (estado IN ('activo', 'inactivo'))
```

La fecha de instalación no deberá ser futura según la fecha de ejecución de la carga. Esta validación se realizará durante la inserción o mediante lógica de aplicación, evitando una restricción `CHECK` dependiente de la fecha actual.

### 2.7. VARIABLE_MEDICION

| Columna | Tipo de dato | Permite NULL | Restricciones |
|---|---|---|---|
| `id_variable` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | No | PRIMARY KEY |
| `nombre_variable` | `VARCHAR(120)` | No | NOT NULL, UNIQUE |
| `unidad_canonica` | `VARCHAR(40)` | No | NOT NULL |

**Descripción:** almacena las variables medidas por los sensores y sus unidades canónicas.

**Consideraciones:**

- Cada variable posee una única unidad canónica.
- El nombre de cada variable debe ser único.
- Los valores deben convertirse a su unidad canónica antes de almacenarse.
- Las unidades deben ser compatibles con las convenciones de medición acordadas.

**Ejemplos presentes en el contrato MongoDB:**

| Variable | Unidad canónica |
|---|---|
| `temperatura` | `°C` |
| `pm25` | `µg/m³` |

Estos valores son ejemplos de la muestra de MongoDB y no constituyen el catálogo definitivo.

### 2.8. MEDICION

| Columna | Tipo de dato | Permite NULL | Restricciones |
|---|---|---|---|
| `id_medicion` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | No | PRIMARY KEY |
| `id_sensor` | `VARCHAR(64)` | No | FOREIGN KEY, NOT NULL |
| `id_variable` | `BIGINT` | No | FOREIGN KEY, NOT NULL |
| `fecha_utc` | `TIMESTAMPTZ` | No | NOT NULL |
| `valor` | `NUMERIC(18,6)` | No | NOT NULL |
| `fuente` | `VARCHAR(180)` | No | NOT NULL |

**Claves foráneas:**

- `id_sensor` → `sensor(id_sensor)`
- `id_variable` → `variable_medicion(id_variable)`

**Descripción:** almacena las observaciones registradas por los sensores.

**Consideraciones:**

- Cada medición pertenece a un sensor.
- Cada medición corresponde a una variable.
- Se registra la fecha y hora de la observación.
- Se almacena la procedencia mediante el atributo `fuente`.
- Los valores se almacenan utilizando la unidad canónica de su variable.
- La precisión de `NUMERIC(18,6)` debe validarse con los datasets reales.

No se establece por ahora una restricción `UNIQUE` sobre la combinación de sensor, variable y fecha, debido a que podrían existir mediciones provenientes de diferentes fuentes o reprocesamientos.

La política para identificar y gestionar registros duplicados se definirá al preparar la carga.

## 3. Relaciones y claves foráneas

| Tabla hija | Clave foránea | Tabla referenciada | Clave primaria | Cardinalidad |
|---|---|---|---|---|
| `tipo_sensor` | `id_categoria` | `categoria_sensor` | `id_categoria` | N:1 |
| `sensor` | `tipo_sensor` | `tipo_sensor` | `tipo_sensor` | N:1 |
| `sensor` | `id_ubicacion` | `ubicacion` | `id_ubicacion` | N:1 |
| `sensor` | `id_organismo` | `organismo_responsable` | `id_organismo` | N:1 |
| `medicion` | `id_sensor` | `sensor` | `id_sensor` | N:1 |
| `medicion` | `id_variable` | `variable_medicion` | `id_variable` | N:1 |

**Resultado del modelo:**

- 8 tablas.
- 8 claves primarias.
- 6 claves foráneas.
- Todas las relaciones son 1:N.
- Todas las claves foráneas son obligatorias.
- `USUARIO` permanece independiente.

## 4. Compatibilidad con MongoDB

El contrato de MongoDB establece cuatro colecciones:

- `lecturas`
- `eventos`
- `alertas`
- `incidentes`

Los identificadores de sensores y ubicaciones deben mantenerse sincronizados con PostgreSQL.

### 4.1. Equivalencia de atributos

| PostgreSQL | MongoDB | Compatibilidad |
|---|---|---|
| `sensor.id_sensor` | `sensor_id` | Identificador textual compartido |
| `ubicacion.id_ubicacion` | `zona_id` | Identificador textual compartido |
| `sensor.tipo_sensor` | `tipo_sensor` | Código de tipo de sensor |
| `variable_medicion.nombre_variable` | `variable` | Nombre de variable |
| `variable_medicion.unidad_canonica` | `unidad` | Unidad de medición |
| `medicion.fecha_utc` | `fecha` | Instante UTC |
| `medicion.valor` | `valor` | Valor numérico |
| `medicion.fuente` | `fuente` | Procedencia de los datos |

### 4.2. Identificadores compartidos

PostgreSQL:

```sql
id_sensor VARCHAR(64) PRIMARY KEY
```

MongoDB:

```javascript
{
  sensor_id: "S001"
}
```

Ambos sistemas deberán utilizar el mismo identificador.

De forma equivalente:

- PostgreSQL: `ubicacion.id_ubicacion`
- MongoDB: `zona_id`

Los identificadores deben conservar exactamente sus valores, incluidos prefijos y ceros iniciales.

Los valores como `S001` son ilustrativos; el catálogo definitivo se coordinará con el equipo.

### 4.3. Unicidad de identificadores

En PostgreSQL:

- `sensor.id_sensor` es único.
- `ubicacion.id_ubicacion` es único.

En MongoDB:

- `_id` es único dentro de cada colección.
- `sensor_id` puede repetirse entre múltiples lecturas.
- `zona_id` puede repetirse entre múltiples documentos.

Por lo tanto, no debe imponerse unicidad sobre `lecturas.sensor_id`.

### 4.4. Fechas y unidades

En PostgreSQL:

- `fecha_utc` utiliza `TIMESTAMPTZ`.

En MongoDB:

- `fecha` utiliza BSON Date.

Ambos representan instantes de tiempo que se interpretarán y consultarán en UTC.

Las variables y unidades deben utilizar convenciones consistentes entre ambos sistemas.

### 4.5. Datos sintéticos

MongoDB utiliza el campo booleano `sintetico` para distinguir datos generados de observaciones reales.

El modelo PostgreSQL aprobado todavía no incluye ese atributo.

Queda pendiente decidir si se agrega a `medicion` o si se utiliza otro mecanismo de trazabilidad.

Cualquier modificación deberá actualizar el modelo relacional, el diccionario de datos y los scripts correspondientes.

## 5. Orden de creación de tablas

El archivo `postgres/01_schema.sql` deberá crear las tablas en un orden que respete las dependencias de las claves foráneas:

1. `ubicacion`
2. `categoria_sensor`
3. `tipo_sensor`
4. `organismo_responsable`
5. `usuario`
6. `variable_medicion`
7. `sensor`
8. `medicion`

Este orden permite crear todas las relaciones sin referencias a tablas inexistentes.
