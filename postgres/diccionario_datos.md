# SmartCity Analytics — Diccionario de datos PostgreSQL

**Estado:** actualizado tras las auditorías EPA AQS; coincide con `postgres/01_schema.sql` versión inicial. Reglas de ETL y calidad aún pendientes.  
**Motor:** PostgreSQL 16  
**Alcance:** ocho tablas del modelo lógico relacional acordado.

## 1. Convenciones de implementación

- Nombres de tablas y columnas en `snake_case`, sin tildes, dentro del esquema `public`.
- Los IDs compartidos con MongoDB (`id_sensor`, `id_ubicacion`) se almacenarán como `VARCHAR(64)` para conservar ceros iniciales y prefijos alfanuméricos. El contrato MongoDB confirma que `sensor_id` y `zona_id` son **cadenas estables** coordinadas con PostgreSQL; **el límite de 64 caracteres sigue siendo una propuesta local**, que Edward y el equipo deben respetar o renegociar.
- IDs de catálogos y entidades internas (`id_categoria`, `id_organismo`, `id_usuario`, `id_variable`, `id_medicion`) se proponen como `BIGINT GENERATED BY DEFAULT AS IDENTITY` para facilitar cargas reproducibles con ID explícito, cuando corresponda.
- En campos de texto, `VARCHAR(n)` expresa el límite máximo acordado en esta propuesta, no un requisito del enunciado.
- Las fechas de instalación usan `DATE`; los instantes de medición usan `TIMESTAMPTZ`, representados e intercambiados en UTC.
- Las seis FK del lado N serán `NOT NULL` conforme a las participaciones totales del Chen.
- Para evitar pérdida de historia, se propone `ON DELETE RESTRICT` en las FK. Sin borrado en cascada.
- Se confirma `UNIQUE` para `categoria_sensor.nombre_categoria`, `variable_medicion.nombre_variable` y `usuario.correo`. Los nombres de personas no son únicos.
- `usuario.apellido2` es opcional (`NULL` permitido).
- `sensor.estado` solo admite `activo` e `inactivo`.

La transformación de unidades debe realizarse **antes** del INSERT, según la variable; la FK por sí sola no convierte unidades.

### 2.8 `medicion`

| Columna | Tipo propuesto | Nulo | Regla |
|---|---|---|---|
| `id_medicion` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | No | PK |
| `id_sensor` | `VARCHAR(64)` | No | FK a `sensor(id_sensor)` |
| `id_variable` | `BIGINT` | No | FK a `variable_medicion(id_variable)` |
| `fecha_utc` | `TIMESTAMPTZ` | No | Almacenar y consultar instantes en UTC; entregar timestamps con zona |

Ambas FK proponen `ON DELETE RESTRICT`. **No se impone todavía** `UNIQUE(id_sensor,id_variable,fecha_utc)` porque distintas fuentes o reprocesamientos podrían producir mediciones legítimas para el mismo instante; decidir una política de duplicados según los datasets.

## 4. Contrato de interoperabilidad con MongoDB

El contrato inicial elaborado para MongoDB usa las colecciones `lecturas`, `eventos`, `alertas` e `incidentes`. Establece que `sensor_id` y `zona_id` son cadenas estables coordinadas con el catálogo PostgreSQL, pero **no fija su longitud máxima**. Esta tabla es un mapeo entre modelos, no una declaración de claves foráneas en MongoDB.

| PostgreSQL | MongoDB | Acuerdo |
|---|---|---|
| `sensor.id_sensor` | `sensor_id` | Mismo identificador textual del sensor; PostgreSQL lo declara PK, MongoDB permite repetirlo entre lecturas |
| `ubicacion.id_ubicacion` | `zona_id` | Mismo identificador textual de la ubicación/zona |
| `sensor.tipo_sensor` | `tipo_sensor` | Mismo código de tipo de sensor |
| `variable_medicion.nombre_variable` | `variable` | Misma denominación de la variable |
| `variable_medicion.unidad_canonica` | `unidad` | Misma unidad canónica para valores comparables |
| `medicion.fecha_utc` | `fecha` | Instante UTC (`TIMESTAMPTZ` en PostgreSQL; BSON Date en MongoDB) |
| `medicion.valor` | `valor` | Valor numérico; las conversiones se realizan durante la carga |
| `medicion.fuente` | `fuente` | Procedencia del dato |

**Ejemplos existentes en la muestra de MongoDB:** `termometro` / `temperatura` / `°C` y `particulas` / `pm25` / `µg/m³`. No son el catálogo definitivo. La carga y las consultas deben respetar una escritura consistente.

MongoDB distingue las observaciones sintéticas mediante el campo booleano `sintetico`. El modelo PostgreSQL aprobado aún no contiene ese atributo: **queda pendiente decidir si se agrega a `medicion`**, o si su trazabilidad se documenta mediante otro mecanismo; añadirlo requeriría actualizar el modelo y este diccionario. El `_id` de las colecciones MongoDB identifica documentos y **no sustituye** a `sensor_id` ni a `zona_id`.

5. Política de mediciones duplicadas y rangos válidos de `valor` según variable.

## 4. Reglas de carga EPA AQS pendientes de implementación

- Las auditorías locales identificaron 20.994 estaciones, 370.090 monitores y 12.316.717 mediciones entre PM2.5 y PM10; no implican datos cargados en PostgreSQL.
- La combinación de códigos State/County/Site identifica la ubicación; añadir Parameter/POC identifica el monitor. Conservar ceros a la izquierda.
- `Local Site Name` falta en una gran proporción del catálogo: derivar un nombre descriptivo identificado como generado, si se mantiene `nombre_zona NOT NULL`.
- Para EPA, `distrito` utilizará `County Name` como aproximación administrativa explícita, no equivalencia exacta.
- `Collecting Agency`, `Reporting Agency` y `Owning Agency` tienen roles distintos; seleccionar con procedencia registrada. No inventar el contacto `responsable`.
- `First Year of Data` no equivale a `fecha_instalacion`. `Last Sample Date` no prueba condición física operativa. Clasificar `estado` con una política ETL reproducible.
- Los archivos horarios incluyen negativos, calificadores de calidad y condiciones de unidad (LC/25 C). Conservar originales y fijar política antes de filtrar o convertir.
- No se impone aún unicidad de `(id_sensor, id_variable, fecha_utc)` para admitir fuentes y reprocesamientos; la deduplicación debe tratarse en el ETL.
